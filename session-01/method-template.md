# 把一次有效工作寫成方法

把以下內容複製到自己工作區 `my-work/research/` 的 Markdown 檔，再按材料修改。先用一頁／一張圖試做；這是可重用的工作規則，不是模型權重訓練。不同 agent 的 skill 存放和載入方式不同，請讓自己的工具說明並確認它實際讀了此檔。

## 兩條核心原則（全程遵守）

1. **這個想法是誰的？（Whose idea is this?）**：在每份筆記與表格中，明確區分（a）原材料直接顯示／寫出的內容、（b）你自己的觀察與判斷、（c）既有學者的研究結論，以及（d）AI 提出的候選描述或假說。
2. **這條資訊從哪裡來？（Where did this information come from?）**：每一步 OCR、翻譯、視覺描述或表格提取，都必須保留 `source_id`、檔案名稱、印刷頁碼／掃描頁序或圖像裁切區域座標，隨時能指回 `my-work/sources/raw/`。

## 目的與範圍

我想回答的研究問題：……

本次只處理：……（列明 `my-work/sources/raw/` 中的檔案／頁面／版本）。不以模型記憶補寫來源沒有的歷史事實。

## 輸入與四層資料夾位置

- `my-work/sources/raw/`：保留原始圖像與 PDF 不改動。
- `my-work/sources/processed/`：存放 OCR（先試 OpenRouter 視覺 LLM／DeepSeek Vision → 古籍／豎排題跋再試 PaddleOCR API → 最後才用 agent 內建看圖）、裁切圖、暫譯與結構化 CSV 表格。
- `my-work/research/`：存放閱讀筆記、本方法檔、圖像生成「純文字 vs 史料約束」並排比較，或 3D／虛擬空間的 **「有據（Evidenced）／推論（Inferred）／虛構補全（Invented）」三欄表**。
- `my-work/artifacts/`：存放不進 Git 的大型輸出（`.glb`／`.blend` 模型、批次生成圖、遊戲引擎匯出、SQLite 資料庫、embeddings）。

## 步驟

1. 確認材料可讀及本次要處理的單位。
2. 按指定欄位產生候選。保留原詞；正規化、翻譯及推測另列。
3. 每項附原文／可見描述及頁碼或區域。未知寫未知，不為了填滿表格猜測。
4. 查重複、單位、日期、身份與欄位角色；例如出土地與現收藏地分開。
5. 回原材料核對有用候選，另看未命中材料是否漏取。未核對的不標成已確認。

## 輸出

一份小候選表或比較記錄：記錄 `id`、原詞／觀察、整理欄位、來源定位、想法歸屬（史料／研究者／學界／AI）、核查狀態與疑點。若為 3D 或空間重建，附上 `Evidenced / Inferred / Invented` 三欄表。

## 停止、測試與現代 Skill 編寫手藝（30 分鐘停止原則）

1. **直接用清楚的自然語言撰寫（少做死板機械限制）**：現在的強模型不需要複雜偽代碼，用清楚的自然語言（甚至一大段連貫文字）把你的背景 Context、目的與擔憂（Worries）說清楚即可，給模型留出發揮空間。
2. **關鍵限制與 Instruction 放在最後面（Recency Effect）**：模型對放在中間的指令最容易忽略（Lost in the Middle）；把最關鍵的硬約束（例如「只列畫面可見事實、不加外部知識」「必須附帶頁碼與原句定位」「數據必須全量真實連通，禁止在 HTML 或 Search 框裡寫死假結果」）放在這份 Skill 的**最後面**，離模型開始生成的地方最近，權重最高。
3. **在同一個問題／樣本上反覆試，觀察 `Behavior Change`**：材料不可讀、來源無法定位、同名無法判定、表格關係不清或權限不足時，保存疑點並停下該項。若工具或環境設定卡住超過 30 分鐘，立即停下並把具體錯誤寫進 `my-work/questions.md`。
4. **記錄一次具體迭代**：哪個例子、錯在哪、改了哪一句自然語言規則、在同一個樣本上看到了什麼 `Behavior Change`，再拿一個新例子核查；方法改動後用 Git 保留版本與理由。

最後寫一句：這次結果能支持甚麼，仍不能支持甚麼。
