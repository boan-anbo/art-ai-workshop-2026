<strong>假設情境 · 英文：</strong>

<details class="original-question">
<summary>English · hypothetical scenario</summary>
<blockquote lang="en">Suppose a project extracts object records from archaeological or survey reports to build a database. How could the workflow and its accuracy be improved?</blockquote>
</details>

假設有上述研究情境，可以從以下方法開始。

可行。先確認一條記錄代表一件器物、殘片還是一組材料，再用一份報告的小樣本定欄位。正文、表格與圖版可能重複描述同一件器物，必須處理識別碼與重複計數。

要求每個提取值帶原文、頁碼或圖版位置；保留原標法，另外做名稱和單位規範化。準確性既包括<strong>值有沒有讀錯，也包括漏件與重複</strong>。人工對照樣本要包含跨頁表格、缺值和難例，再按 OCR、讀序、提取、合併等錯誤修訂方法。

可先用 CSV，確實需要多表連接時再用 SQLite。[LangExtract](https://github.com/google/langextract) 等工具可協助把提取連回文字位置，結果仍要核查。Workshop 會從少量器物資料走完提取、查驗與一次修訂。

批量實作時，不要把整本報告塞進一次漫長對話。我會讓 coding agent 透過<strong>獨立 API calls，每次處理約 1–3 頁或 1–3 段</strong>，同時帶入這份報告的遺址、年代與必要上下文。先存 raw extractions，再與 agent 討論清理和資料模型，最後才納入正式資料庫；這三層分開，才方便追查錯誤。

對每條摘錄保存可回查的頁、行與原句；有穩定文字層時再保留字符位置，讓確定性腳本核對引文是否確實存在。這能抓出錯抄或定位失效，卻不能單獨判斷解讀對錯。再讓另一輪強模型作 Judge，把原文與結果並排檢查，人工集中處理爭議及最後真正支撐論點的記錄。
