<strong>假設情境 · 英文：</strong>

<details class="original-question">
<summary>English · hypothetical scenario</summary>
<blockquote lang="en">Suppose a map needs to show excavated objects from a historical period, such as a class of ceramics or bronzes, while distinguishing site types, quantities and object categories. How could AI and GIS help?</blockquote>
</details>

可以，先決定讀者要比較甚麼，再分配視覺符號。可試：形狀表示遺址類型、點的面積表示數量、顏色表示器物類別；同一遺址有多個品種時，分面小圖或切換圖層往往更容易讀。

[QGIS 的符號與圖表設定](https://docs.qgis.org/3.44/en/docs/user_manual/working_with_vector/vector_properties.html) 支援這些表達方式，但圖例和數量單位需要你定義。不能把碎片數、完整器數及精選標本數直接合計；未知也不是零。

用遺址 id 連接資料，檢查連接後是否重複計數。近似位置與精確位置要有所區別，並註明時段、來源及覆蓋缺口。

也可以把需求直接告訴 coding agent，讓它先做可操作的互動地圖原型：切換遺址類型、依數量調整大小、篩選不同器物類別或窯口／產地類型。現在「Make it happen」的第一步常常很快；真正關鍵是<strong>第 2、3、4 步的使用、檢查與迭代</strong>。

特別追查完整的 <strong>data chain（數據鏈）</strong>：搜尋是否真的查底層資料，還是不管輸入甚麼都回那幾條寫死的結果？畫面是否從完整 CSV／JSON／資料庫導入、轉換並可更新，還是只把幾行數據抄進 HTML 湊效果？試不同詞、空結果、增添與修改一條記錄，要求 agent 展示從原始資料到畫面的路徑。

把擔憂寫進自然語言 Skill：資料完整連通、模組清楚、可長期維護、錯誤可見、測試與日誌可查，並說明預期資料量和縮放／篩選的流暢度。可請它比較 Mapbox GL、deck.gl 等方案，選擇符合需求的工具；不能只因用了較新的庫就認定工程品質合格。

Workshop 會用同一小份資料比較不同畫法，挑能讓研究問題看清楚的一種；不必把所有維度塞在同一畫面。

讓 agent 對 join 前後的總件數寫一條檢查，防止器物表與遺址表的一對多連接把數量翻倍；紙本論文另匯出同底圖、按器物類別分開的小分面圖，方便讀者比較。
